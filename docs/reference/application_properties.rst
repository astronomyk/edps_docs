``application.properties`` reference
====================================

The complete configuration file as generated by EDPS 1.7.1 on first run, at
``~/.edps/application.properties``. Defaults shown are the as-generated values.

.. important::

   The EDPS server caches this file at startup. After any change, run
   ``edps -shutdown`` before the next request.

The file is INI-style with seven sections. The source manual (written against
EDPS 1.3.3) describes these keys as a flat list; the sections were introduced
later.


``[server]``
------------

.. list-table::
   :header-rows: 1
   :widths: 22 14 64

   * - Key
     - Default
     - Description
   * - ``host``
     - ``0.0.0.0``
     - Host or IP address to which the EDPS server binds, e.g. ``localhost`` or
       ``0.0.0.0``.
   * - ``port``
     - ``5000``
     - EDPS port number.


``[application]``
-----------------

.. list-table::
   :header-rows: 1
   :widths: 22 14 64

   * - Key
     - Default
     - Description
   * - ``workflow_dir``
     - *(empty)*
     - Comma-separated list of directories where workflows are installed. If not
       specified, EDPS searches for workflows in the pipeline installation tree.
       The naming convention is ``<instrument>/<instrument>_wkf.py``, e.g.
       ``espresso/espresso_wkf.py``.


``[executor]``
--------------

.. list-table::
   :header-rows: 1
   :widths: 26 20 54

   * - Key
     - Default
     - Description
   * - ``esorex_path``
     - ``esorex``
     - The command to execute pipeline recipes, installed with the pipeline.
       Make sure the path provided can be located using ``which``.
   * - ``pipeline_path``
     - *(empty)*
     - Path where pipeline plugins are installed. ESO-internal; can be left
       empty.
   * - ``genreport_path``
     - ``genreport``
     - The command to execute quality-control plots, installed with the Adari
       package.
   * - ``base_dir``
     - ``~/EDPS_data``
     - EDPS data directory where recipe products, logs and QC plots are saved.
       Files are organised as
       ``<instrument>/<task>/<unique-id>/<files>``. Ensure enough disk space,
       and consider enabling ``[cleanup]``.
   * - ``dummy``
     - ``False``
     - If true, a dummy command is executed instead of ``esorex``.
   * - ``continue_on_error``
     - ``False``
     - If true, EDPS attempts to execute a data reduction step even if the
       previous step failed.
   * - ``processes``
     - ``1``
     - Number of concurrent data reduction processes. Increases performance if
       resources allow, but can lead to pipeline crashes if memory is
       insufficient.
   * - ``cores``
     - ``1``
     - Number of CPU cores available for data reduction. EDPS will not exceed
       this when scheduling tasks.
   * - ``default_omp_threads``
     - ``1``
     - Recipes are parallelised with OpenMP. EDPS sets
       ``OMP_NUM_THREADS = min(default_omp_threads, cores)``.
   * - ``ordering``
     - ``bfs``
     - Execution ordering: ``dfs``, ``bfs``, ``type``, ``dynamic``. All follow
       topological order. See below.
   * - ``output_prefix``
     - *(empty)*
     - If provided, products are renamed
       ``<prefix>.<instrument>.YYYY-MM-DDThh:mm.ss.mss.fits``. Renaming occurs
       in the base directory, not the package (output) directory.
   * - ``resume_on_startup``
     - ``False``
     - If EDPS was stopped while jobs were waiting, execute them after restart.
   * - ``reexecution_window_minutes``
     - ``60``
     - EDPS will re-execute a failed job needed as an association, but only
       within this window.
   * - ``save_report_inputs``
     - ``False``
     - Extract input files from the reporting-script output and store them in
       the execution result. Significantly increases the database size.

Execution ordering values
~~~~~~~~~~~~~~~~~~~~~~~~~

``dfs``
   Depth-first — give preference to reaching the final reduction target quicker.

``bfs``
   Breadth-first — follow the reduction cascade level by level. **Default.**

``type``
   Same as ``bfs``, but process the same type of data together (e.g. first all
   biases).

``dynamic``
   Immediately run whichever job is ready; no stalling, but the order is
   unpredictable.

.. note::

   The source manual gives the default as ``dfs`` and does not list ``bfs``.


``[generator]``
---------------

.. list-table::
   :header-rows: 1
   :widths: 28 24 48

   * - Key
     - Default
     - Description
   * - ``calibrations_config_file``
     - *(empty)*
     - YAML file defining locations of static calibrations per workflow.
       ESO-internal; EDPS loads static calibrations delivered with the pipeline
       automatically.
   * - ``parameters_config_file``
     - *(empty)*
     - YAML file defining locations of recipe and workflow parameters per
       workflow. ESO-internal.
   * - ``association_preference``
     - ``raw_per_quality_level``
     - Which calibrations to use when several match. See below.
   * - ``breakpoints_url``
     - ``https://archive.eso.org/calselector/v1/breakpoints``
     - URL to ESO-provided list of calibration breakpoints.
   * - ``associate_incomplete_jobs``
     - ``True``
     - Associate incomplete jobs if no complete job is available.
   * - ``associate_existing_jobs``
     - ``False``
     - Associate jobs created in previous reductions.
   * - ``keep_request_files``
     - ``False``
     - Keep in memory files submitted as part of reduction or organisation
       requests so they can be used as associations in subsequent requests.
   * - ``meta_workflow``
     - *(empty)*
     - Comma-separated list of workflows to combine into one, allowing data from
       different instruments to be submitted to ``edps.workflow.meta_wkf``.

Association preference values
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

``raw``
   Use reduced raw data results even if master calibrations closer in time are
   available.

``master``
   Use master calibrations even if results of reduced raw data closer in time
   are available.

``raw_per_quality_level``
   Use calibrations closest in time but prefer reduced raw data results.
   **Default.**

``master_per_quality_level``
   Use calibrations closest in time but prefer master calibrations.

.. seealso:: :doc:`../user_guide/configuration` and :ref:`raw-or-master`.


``[repository]``
----------------

.. list-table::
   :header-rows: 1
   :widths: 24 22 54

   * - Key
     - Default
     - Description
   * - ``truncate``
     - ``False``
     - Clear the EDPS bookkeeping database on startup. Causes all tasks to be
       re-executed even if previously executed on the same data.
   * - ``local``
     - ``True``
     - Use a local database for bookkeeping (currently always ``True``).
   * - ``path``
     - ``<base_dir>/db.json``
     - Path where the bookkeeping database is stored.
   * - ``type``
     - ``caching``
     - Database type: ``tiny`` (TinyDB JSON file), ``memory`` (fast in-memory,
       non-persistent), ``caching`` (in-memory cache on top of persistent
       TinyDB, for higher performance).
   * - ``flush_size``
     - ``10``
     - How many changes trigger TinyDB flushing to disk.
   * - ``flush_timeout``
     - ``60``
     - How often data should be flushed automatically, regardless of changes.
   * - ``min_disk_space_mb``
     - ``100``
     - Minimum available disk space (MB) required to flush data to disk.


``[cleanup]``
-------------

.. list-table::
   :header-rows: 1
   :widths: 34 18 48

   * - Key
     - Default
     - Description
   * - ``enabled``
     - ``False``
     - Enable automatic cleanup of reduced data.
   * - ``cleanup_older_than_seconds``
     - ``1209600``
     - How much time must pass since data were reduced to consider them for
       removal (default: 14 days).
   * - ``cleanup_check_period_seconds``
     - ``3600``
     - How often to check whether there are data to be removed.

.. note::

   This whole section is absent from the source manual. It is the intended
   answer to an ``EDPS_data`` directory that grows without bound.


``[packager]``
--------------

.. list-table::
   :header-rows: 1
   :widths: 24 26 50

   * - Key
     - Default
     - Description
   * - ``package_base_dir``
     - *(empty)*
     - Location where selected products should be placed.
   * - ``mode``
     - ``copy``
     - How to place files: ``link`` (hardlinks), ``symlink`` (symbolic links),
       ``copy``.
   * - ``pattern``
     - ``$DATASET/$TIMESTAMP/$object$_$pro.catg$.$EXT``
     - Directory and filename pattern. See variables below.
   * - ``categories``
     - *(empty)*
     - Comma-separated list of product categories to place in the package
       directory. Empty means all products matching the reduction target.
   * - ``skip_conflicting``
     - ``True``
     - ``True`` skips packaging if the target filename already exists; ``False``
       adds a ``_{i}`` suffix with increasing ``i``.

Pattern variables
~~~~~~~~~~~~~~~~~

The pattern can contain any string, header keywords enclosed in ``$`` (e.g.
``$pro.catg$``), and the following predefined special variables:

.. list-table::
   :header-rows: 1
   :widths: 20 80

   * - Variable
     - Meaning
   * - ``$NIGHT``
     - Year-month-day of when the data were taken.
   * - ``$FILENAME``
     - Original name of the file.
   * - ``$EXT``
     - Original extension of the file name.
   * - ``$TASK``
     - Name of the EDPS task which produced the file.
   * - ``$TIMESTAMP``
     - Timestamp when data were submitted for reduction.
   * - ``$DATASET``
     - Dataset name, derived from the first raw input file.

.. note::

   ``$NIGHT``, ``$FILENAME`` and the ``symlink`` mode are not documented in the
   source manual.
